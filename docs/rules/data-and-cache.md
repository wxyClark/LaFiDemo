# MySQL 8.4 与 Redis 开发规范

## 1. MySQL 作为交易事实来源

### Schema 与数据类型

- 使用 InnoDB、`utf8mb4` 字符集及团队统一的排序规则；SQL mode 使用严格模式。连接字符集、时区和隔离级别应在环境配置中一致。
- 每张业务表按使用场景明确主键、时间戳、软删除策略。支付、库存流水、订单快照、审计和佣金账目等事实不可因普通删除请求被级联抹除。
- 货币以整数最小单位存储并保存 `currency_code`；价格区间和历史快照明确生效时间。不要用 `FLOAT`/`DOUBLE` 保存货币。
- 整数数量适用于整件商品；称重/计量场景明确单位、精度与舍入规则，优先使用整数最小单位或 `DECIMAL(p,s)`，严禁浮点参与计费。
- JSON 仅用于低频、结构可变且不常参与关系约束/筛选的配置或快照；稳定业务字段应使用明确列。禁止把整套关系模型塞进一个 JSON 字段。
- 所有租户业务表显式包含 `tenant_id`；租户组合唯一键如 `(tenant_id, sku)`。外键尽可能保证同租户关联，无法由数据库表达时用应用校验和集成测试补强。
- 选择 `VARCHAR` 长度、NULL/默认值和删除规则应按领域含义确定；避免无边界 `TEXT` 承载本该索引/约束的业务 key。

### 数据表常用字段基线

- 主键：业务表统一自增 `BIGINT UNSIGNED` 主键；对外标识（订单号、SKU 等）作为业务唯一键（含 `tenant_id` 的组合 `UNIQUE`）单独建列，不直接用自增主键对外暴露。
- 时间戳：`created_at`/`updated_at`，存 UTC；事实/流水表必须保留 `created_at` 供审计，只追加表可省略 `updated_at`（在迁移中显式声明）。
- 多租户：所有租户业务表非空 `tenant_id`，并入唯一键与索引前缀（见上节）；跨租户访问一律经 TenantContext + Policy，表中不得出现"全局表"豁免而不经评审。
- 金额/数量：货币为整数最小单位 + `currency_code`（ISO 4217）；数量用 `UNSIGNED INT` 或称重场景 `DECIMAL(p,s)`，禁止浮点（见上节）。
- 状态/枚举：存 `VARCHAR` 枚举码，代码内 enum 做映射与校验（大小写风格随模块既有约定）；禁止存无稳定映射的枚举序号。
- 软删除：按需使用 `deleted_at`；事实表（流水、审计、订单快照）只追加、禁止软删；级联删除规则在建表迁移中逐表写明。
- 迁移文件必须显式写出各列的默认值、NULL 性与删除规则；同模块扩列遵循 expand-and-contract（delivery-and-operations §3）。

### 索引与查询

- 索引从实际查询模式设计；高频条件通常将等值过滤列（如 tenant_id）放在复合索引前部，再考虑排序/范围列。结合真实 `EXPLAIN` 和数据分布验证，不机械套用固定顺序。
- 为唯一业务标识、外键查询、租户列表页和队列扫描建立必要索引；控制冗余索引和宽索引对写入、存储的成本。
- 列表必须分页并设置最大页长；只取需要列；避免 N+1、无条件全表扫描和在循环内逐条写入。
- 搜索条件必须参数化；用户可选排序列/筛选字段使用白名单。慢查询需有阈值、采样/观测与定位记录，生产诊断避免暴露个人信息。
- 大批量更新/删除采用可控批次、游标/主键范围和限速；评估锁等待、复制延迟和回滚成本。

### 事务、锁和并发

- 事务保护单库原子业务操作；事务越短越好。不得持有行锁期间调用网络服务或等待用户输入。
- 库存扣减优先使用数据库事务 + `SELECT ... FOR UPDATE` 或带库存条件的原子更新，并检查受影响行数；唯一键/约束防止重复记录。验证并发请求不会超卖。
- 采用固定的锁获取顺序减少死锁；对可重试的死锁/锁超时使用有限次数、带抖动重试，并确保整个用例幂等。
- 隔离级别与一致性要求明确。不要用“读后写”无锁模式处理库存、优惠名额、退款累计等并发敏感数据。
- 不在同一请求随意跨数据库连接做“假事务”；跨服务/外部渠道通过 Saga/补偿或 Outbox，而非分布式锁假装原子性。

### 迁移与数据治理

- 所有结构变更提交 Laravel migration；手工 SQL 生产改动需纳入迁移历史或正式变更记录。
- 先加兼容列/索引，再部署兼容代码，回填并验证，最后在后续发布删除旧结构（expand-and-contract）。大型索引创建策略依托目标 MySQL/云服务能力验证。
- 数据库备份必须定期恢复演练；定义 RPO/RTO、加密、访问控制、异地保存及备份保留期。
- 生产数据禁止复制到开发/测试；确需调试时用脱敏、最小字段、受控访问和可审计副本。

## 2. 电商核心表一致性

- 订单总额必须可复算：商品小计、优惠、运费、税费、调整项和最终金额有明细及快照。币种一致，退款累计不得超过可退金额。
- 订单行快照独立于商品当前状态；修改商品标题、SKU、价格、地址不改变历史订单事实。
- `inventory_balances` 是可快速读取的余额投影，`inventory_movements` 是审计账本。每次调整有来源、原因、幂等标识和操作者；流水不可静默更新/删除。
- 状态变更由应用用例检查允许转换，并记录 from/to、时间、执行者/来源和原因。支付状态、履约状态、订单状态相互独立。
- 关键写入使用数据库唯一约束防重：幂等请求、第三方支付事件、渠道订单号、租户 SKU 等；应用层先查不能替代唯一约束。

## 3. Redis 规范

### 用途边界

允许用于：缓存、Laravel Queue、限流计数、短期协调、可重建的临时数据。Redis 不作为商品价格、订单支付结果、库存账本或佣金账本的唯一权威源。缓存丢失不得破坏交易事实。

### Key、TTL 与隔离

- Key 使用统一命名空间，至少包含环境和业务域；多租户键包含可信 tenant ID，例如 `prod:catalog:t:{tenantId}:...`。
- 所有非永久键定义 TTL、容量估算、过期策略和失效方式；禁止无界缓存用户输入和无限增长集合。
- 避免把个人信息、令牌、支付敏感载荷放入缓存；若业务确需短暂缓存，需加密/访问控制、短 TTL 和清理策略。
- 缓存穿透/击穿/雪崩按业务负载设计空值缓存、请求合并、随机 TTL 和降级；缓存更新失败需保证数据库仍可用且结果不越权。
- 缓存 key 必须隔离租户/用户/权限上下文，避免共享缓存将 A 租户数据返回给 B 租户。

### 锁与限流

- 分布式锁必须设置有限 TTL、唯一 owner token，并仅由持有者释放；考虑续租、进程崩溃、网络分区、锁过期后旧持有者继续执行等问题。
- 锁只能减少重复工作或协调短期任务。订单/库存/退款最终正确性必须由 MySQL 事务、条件更新、唯一约束、幂等状态机保障。
- 限流使用明确的身份/租户/IP 维度和降级策略；禁止把可被伪造的客户端头作为唯一身份。

### 队列与可靠事件

- Laravel Queue Job 必须可序列化、可重试、幂等；只传必要标识和租户上下文，不序列化大型模型图或明文秘密。执行时重新加载并校验租户/权限状态。
- 明确 `$tries`、`backoff`、timeout、失败告警和 `failed()` 处理；超时配置需小于 worker/supervisor 的合理终止窗口。设计并发队列时避免重复执行造成重复扣款/出库。
- 关键业务事务与 Outbox 记录同库同事务提交；发布器支持并发领取、租约超时恢复、重复发布幂等和失败重放。不要只依赖“事务提交后 dispatch”保证系统崩溃情况下消息不丢。
- Horizon 仅监控/管理 Redis 队列，不等于消息持久化与业务对账方案。监控 pending、runtime、failed jobs、重试量和队列积压，并按业务 SLA 告警。
- 生产 Redis 明确认证/TLS、网络隔离、内存上限、淘汰策略、持久化/高可用与恢复；应用按依赖故障设计退化。

## 4. 连接与环境

- 应用数据库连接池/连接数、Redis 连接数按 PHP-FPM/队列 worker 总并发估算，避免扩容后连接数乘法超限。
- 本地、CI、预发布和生产尽量使用相同主版本系列；CI 至少有真实 MySQL 与 Redis 服务做集成验证，不能只依赖 SQLite 覆盖 MySQL 专有行为。
- 生产连接串和密码通过 Secret 管理注入，不进入代码、日志、截图或文档；定期轮换高权限凭据。
