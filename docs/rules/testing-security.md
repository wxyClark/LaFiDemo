# Pest 测试、安全与质量门禁规范

## 1. Pest 测试策略

### 分层与命名

- Unit 测试验证不依赖网络/数据库的金额计算、状态机、优惠/佣金规则等领域逻辑，测试名描述业务行为。
- Feature 测试通过 Laravel HTTP、队列、Filament Action 或应用用例验证集成边界：鉴权、Policy、租户隔离、数据库事务、序列化与响应契约。
- 集成测试针对 MySQL/Redis/外部渠道适配；外部服务使用确定性 fake/stub 或官方沙箱，不在常规测试中请求生产服务。
- 测试文件与模块/功能对应，测试数据经 Factory/Builder 创建；不依赖测试执行顺序，不使用共享可变的生产式全局 fixture。
- 用 `RefreshDatabase` 或项目选定的等价策略隔离测试状态；涉及真实并发语义、锁、MySQL 特有约束的测试必须在 MySQL CI 环境运行。
- 避免过度 mock 内部实现；优先断言对外行为、持久化结果和业务不变量。必要时断言 Job/Event 发出及失败策略。

### 必测业务矩阵

对每个写用例，按适用范围验证：

1. 正常成功路径及结果快照；
2. 输入非法、资源不存在、状态不可转换；
3. 未认证、角色不足、对象越权和跨租户访问；
4. 重复请求/重复回调/重复 Job 的幂等行为；
5. 并发边界（库存、优惠券限额、退款累计、佣金结算）；
6. 外部依赖超时、失败、乱序通知和可重试恢复；
7. 事务回滚后没有部分订单、扣库存或孤立 Outbox；
8. 个人信息和敏感字段不会出现在响应、日志或异常详情。

关键电商覆盖：不超卖、重复下单只生成一次事实、支付回调验签与去重、退款不超额、取消/超时释放库存、优惠名额并发、佣金退款冲回、租户资源隔离、Filament 高风险 Action 授权。

### 测试可靠性

- 测试应可在任意顺序、干净数据库和并行 CI 中稳定运行；使用冻结时间/可控 Clock 测过期逻辑，不依赖真实时间等待。
- 不为通过测试而降低生产校验、关闭授权或吞掉异常；禁止 `markTestSkipped` 长期隐藏核心安全测试。
- 外部 HTTP 使用 Laravel HTTP fake/适配器 fake，并验证请求签名/参数（不暴露秘密）。队列可用 fake 断言调度，也需至少有少量真实 worker/序列化集成验证关键 Job。
- 测试名称、断言和注释说明业务意图；一个测试尽量聚焦一个主要行为，可使用 dataset 覆盖清晰的边界集合。
- 修复 Bug 时先添加能复现旧错误的测试，再实现修复。

## 2. 质��工具与 CI

项目初始化后将命令写入 `composer.json`/CI，并保持单一事实来源。推荐门禁：

```text
composer validate --strict
composer audit
vendor/bin/pint --test
vendor/bin/phpstan analyse
vendor/bin/pest
php artisan migrate:fresh --seed --env=testing
```

具体命令以实际锁定的包、配置和 CI 服务为准；不要复制未安装工具命令后宣称已执行。CI 至少固定 PHP 运行版本、安装扩展、启动 MySQL/Redis、安装锁文件依赖并缓存安全可复用部分。

- 合并阻断项：依赖安全检查、格式、静态分析、Unit/Feature 测试和迁移检查。
- 主干分支保护要求 review；涉及支付、租户隔离、权限、迁移和密钥处理的变更需对应领域 reviewer。
- CI 日志应隐藏 secrets；不将 `.env`、数据库 dump、外部 API 真实响应样本作为 artifacts。
- 质量门禁新增规则时先修复或有期限地管理已有基线，禁止无限添加忽略项。

## 3. 安全基线

### 身份、授权与多租户

- 默认拒绝访问，最小权限；认证和授权分离。所有对象访问使用 Policy/Gate 或明确应用授权，不因 ID 难猜而放弃授权。
- TenantContext 来源为认证会话/已验证 membership；检查 membership 活性和资源所属 tenant。平台管理员的跨租户访问需独立权限、审计和必要的原因说明。
- 每个 tenant-owned 表查询与写入均包含 tenant 范围；覆盖 API、后台、队列、导出、Webhook、缓存、通知和异步报表。
- 防止 mass assignment；客户端不能指定租户、支付状态、审计人、佣金状态、计算金额等可信字段。
- 对高风险权限建立拒绝测试；菜单/按钮隐藏不是授权测试的替代。

### Web/API/Webhook

- 全站 HTTPS；浏览器会话启用框架推荐 CSRF 保护、Secure/HttpOnly/SameSite Cookie。CORS 精确白名单。
- 输入长度、格式、类型、文件 MIME/内容/大小都服务端校验；使用参数化查询和安全输出编码。上传文件随机化对象键，禁止执行上传内容。
- 认证、登录、验证码、搜索、下单和 Webhook 设合理速率限制，并按用户/租户/IP/渠道区分策略，监控误伤与绕过风险。
- Webhook 验签使用常数时间比较（由可靠库实现），验证时间戳与重放窗口；事件 ID 唯一持久化。先验证金额、币种、商户及订单关联再改变支付事实。
- 生产错误响应不返回 stack trace、SQL、绝对路径、密钥或支付 payload；对外错误码稳定，内部日志可关联 request ID 且做脱敏。

### 密钥、数据与供应链

- `.env`、密钥、访问 token、支付证书、私钥和客户数据不可提交到 Git；提供无秘密的 `.env.example`。若误提交立即轮换/撤销，不能只删历史文件。
- 日志只记排障必需字段；手机号、邮箱、地址、支付载荷按敏感级别掩码/省略。为审计确定访问控制和保留期限。
- 不保存银行卡 CVV/完整卡数据；使用支付机构托管/令牌化方案。按运营地区进行隐私、税务、消费者保护和支付合规评审。
- 依赖锁定、审查许可证及维护状态、运行安全审计；生产构建可追踪到 commit、依赖锁和镜像摘要。
- 依赖或自动化代码生成的输出要审阅；不得将未验证的外部内容作为可信指令、SQL 或 shell 命令执行。

## 4. 业务审计与故障测试

- 库存调整、退款、手工改价、跨租户管理、佣金冲回/结算需操作者、时间、原因、资源、请求 ID 和脱敏前后值审计。
- 对 Outbox 和支付/库存流程提供对账方式：识别本地与渠道状态不一致、超时、重复事件和待处理积压；修复动作可审计、幂等。
- 失败路径必须保留可诊断上下文但不暴露秘密；明确自动重试与人工介入边界，不无限重试不可恢复业务错误。
