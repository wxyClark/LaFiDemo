# 交付、代码评审与生产运维规范

## 1. Git 与 Pull Request

- 分支和提交信息描述意图；一次 PR 聚焦一个可验证变更，避免无关重构与功能混杂。格式按仓库逐步统一，可采用 Conventional Commits 作为约定。
- PR 描述至少包括：问题/目标、方案、影响模块、租户/权限影响、数据迁移、风险与回滚、验证命令及结果、文档/API 变化。
- 变更保持可审查；大改拆分阶段，明确未完成项。生成文件只在仓库约定需要时提交。
- 至少一名 reviewer 审查一般变更；权限、租户隔离、库存、支付、退款、密钥或破坏性迁移增加对应专业审查。作者必须处理或明确回应所有实质性意见。
- 审查意见按四级严重度分级：**Blocker**（阻止合并/发布，必须解决）、**Must fix**（合并前必须修复或附负责人批准的豁免及期限）、**Should fix**（应修复，可留待后续 PR 并记录）、**Nit**（建议性，不阻断）。该四级体系为仓库唯一审查分级口径；`docs/prompts/prompt-library.md` 模板 4（反向评审）与模板 10（PR Review）输出均使用此分级。作者须对全部 Blocker/Must fix 项给出处理结论（修复或豁免）后方可合并；"实质性意见"指 Blocker 与 Must fix 两级。
- 不把测试失败、静态分析告警或安全扫描问题通过“先合并再说”常态化；紧急例外需负责人批准、记录风险、设置修复期限。

### 多分支并行与冲突处理

- 并行分支保持短生命周期：一任务一分支，CI 通过后尽快合并；长期与 main 漂移（超过 7 天或主干已合并多个其他 PR）的分支必须先同步（优先 rebase；保留记录的需求用 merge）再继续开发。
- 冲突解决归属 PR 作者，在源分支上完成：禁止用“整块取对侧”的方式让冲突消失；解决后必须重跑全部质量门禁（质量 job 与 secret 扫描）并 `git diff` 复核变更仍与原意图一致后方可合并。
- 共享文件（`composer.json`/`composer.lock`、`.github/workflows/`、`docs/rules/`）并行改动时：先完成者先合入，后行分支 rebase 后本地验证门禁仍绿；`composer.lock` 冲突用 `composer update <package>` 重新解析，禁止手工编辑锁文件。
- 多检出使用 `git worktree`：一支一 worktree，互不嵌套；清理 worktree 前先确认无未跟踪产出，有产出先备份再删除。
- PR 合并后及时删除源分支；平台删除接口不可用时记为遗留项集中处理，不无限累积。

## 2. 变更设计与兼容性

- 开始实现前识别调用方、数据归属、状态转换、失败模式、幂等需求和观测指标；跨模块流程先定义接口/事件契约。
- 用户故事/PR 验收标准可验证；技术方案优先小步、可回滚、可观测，避免一次引入多个新基础设施。
- API 对新增可选字段保持兼容；移除/改义需弃用期或新版本。OpenAPI 与实现同步。
- 重大技术取舍、不可逆数据模型和跨模块依赖通过 ADR 记录。ADR 必须包含：背景、决策驱动因素、备选方案（收益/代价）、拟议决策、后果与风险、数据迁移与回滚、验证方式、复核触发条件、决策人/日期；章节结构以 [`docs/adr/TEMPLATE.md`](../adr/TEMPLATE.md) 为唯一模板，新建 ADR 复制该模板填写。状态流转：`Proposed` → `Accepted` → `Deprecated`/`Superseded`；`Proposed` 状态不代表已批准。
- 功能开关适用于渐进发布，但必须有所有者、默认安全值和移除计划；不能用长期 feature flag 隐藏无人维护的分支。

## 3. CI、发布与数据库迁移

- CI 使用提交的 `composer.lock` 安装，固定 PHP/MySQL/Redis 主要版本系列；执行 `composer validate`、依赖安全检查、Pint、PHPStan/Larastan、Pest 与迁移/种子验证。
- 测试关键 MySQL 行为时使用 MySQL 而非只用 SQLite；Redis 队列/缓存集成测试按需运行真实 Redis 服务。
- 发布制品可追溯到代码 commit、依赖锁文件和容器镜像摘要。环境差异通过配置管理，secret 不烘焙进镜像。
- 数据库部署按 expand-and-contract：先加兼容 schema，应用双版本兼容后回填和校验，再单独移除旧结构。长时间回填使用可断点任务，不在发布锁内执行。
- 发布前评估备份、读写兼容、worker 和 scheduler 行为；迁移失败时有明确停止/恢复方案。应用回滚不代表可盲目执行 `migrate:rollback`，先评估数据兼容与备份。
- Horizon/Queue worker 发布时平滑重启，确认旧任务与新代码兼容；队列 Job 版本兼容需纳入部署设计。
- 采用分阶段/灰度发布和健康检查；关键指标异常触发停止扩量或回滚。回滚步骤提前演练，不在故障时首次编写。

## 4. 可观测性与运维

- 应用日志结构化并包含时间、环境、服务、级别、request/correlation ID、模块和业务资源标识；严禁记录密码、token、卡数据、完整 webhook secret 或不必要个人信息。
- 建议监控 HTTP 延迟/错误率、数据库连接/慢查询/锁等待、Redis 内存/连接、队列积压/失败率/任务耗时、支付成功率、库存异常、Outbox 延迟及退款对账。
- 业务告警须有负责人、严重级别、处置指引、抑制重复和升级路径；关键支付/库存告警要能快速定位租户与订单（日志中使用非敏感 ID）。
- 存活检查与就绪检查区分；健康接口不泄露环境变量、服务地址、版本秘密或内部栈信息。
- 定期做 MySQL、对象存储和关键配置的备份恢复演练；记录 RPO/RTO、备份加密、访问审计、保留期和恢复验证结论。
- 队列失败任务重放前确认操作幂等及外部系统状态；生产操作留审计记录并遵循最小权限。

## 5. 事故与复盘

- 故障先止损与保护数据正确性，再恢复功能；支付/库存不确定时暂停自动重复副作用并进入对账流程。
- 记录时间线、用户影响、检测/响应、根因、促成因素和改进项；复盘聚焦系统改进，不以个人归责替代技术措施。
- 改进项需责任人、优先级、完成期限和验证方式；高风险重复故障应增加自动化防护或演练。
