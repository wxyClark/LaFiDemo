# 技术选型：总览、对比与版本决策

> 状态：基线决策（2026-11-03）。本文确定项目的技术方向与版本策略，不意味着依赖已经安装或系统功能已实现。真正初始化项目时，必须按官方兼容矩阵检查并将可复现的精确依赖版本写入 `composer.lock`、容器镜像和部署配置。

## 1. 总览（总）

### 1.1 系统定位

LaFiDemo 是面向在线电商、O2O 和分销场景的 Laravel + Filament SaaS 接口与管理后台参考代码库。采用模块化单体，在一个可运维的 Laravel 应用中保持清晰业务边界；先保证租户隔离、订单/库存/支付正确性和测试质量，再按实际容量与组织边界演进。消费者店铺前端通过稳定 API 解耦，不把 Filament 当作店铺前端。

### 1.2 已确认技术栈与版本策略

| 层次 | 当前选择 | 版本决策 | 核心思考 |
| --- | --- | --- | --- |
| 语言与运行时 | PHP | PHP 最低基线 **8.4.3**（`composer.json` `^8.4.3`，CVE-2024-4577 修复下限）；生产运行 PHP 8.4 分支最新安全补丁版 | Laravel 13 的运行时约束、依赖生态、容器镜像和扩展兼容性共同决定；不只看语言新特性。最终运行版本必须经 CI 全量验证。 |
| Web 应用框架 | Laravel | Laravel 13 | 项目已经以 Laravel 13 为基线；生态成熟，适合快速实现 API、队列、事务、验证、授权、迁移和任务调度。按官方支持政策安排升级。 |
| 管理后台 | Filament | 选择 Laravel 13 / PHP 运行时兼容的受支持稳定主版本；精确主/次/补丁版本在初始化时确认并锁定，不在本文件猜测 | 提升 CRUD、表单、表格和后台交付效率；后台 UI 不是业务授权边界。平台后台与租户后台必须分权。 |
| 主数据库 | MySQL | MySQL 8.4 LTS（CI/集成验证基线：`mysql:8.4` 镜像，见 `.github/workflows/ci.yml` services） | 默认主数据存储。订单、库存、支付等要求事务和约束；团队以单一数据库为基准，降低开发、测试与部署分叉。 |
| 缓存/队列 | Redis + Laravel Cache/Queue | 使用 Laravel 13 支持且云服务/托管环境仍维护的稳定 Redis 版本（CI/集成验证基线：`redis:8` 镜像，见 `.github/workflows/ci.yml` services）；精确版本由服务端与客户端兼容性测试锁定 | 缓存不作为业务事实来源；队列至少一次投递，消费者幂等。库存正确性依赖数据库事务、约束和并发控制，不依赖 Redis 锁单独兜底。 |
| 队列运维 | Laravel Horizon | 选择与 Laravel 13 兼容的稳定版本，随 Composer 锁文件 | 管理 Redis 队列的监控、吞吐和失败任务；不替代告警、重试设计或业务对账。 |
| API | REST `/api/v1` + OpenAPI | API 自身版本从 v1 起；OpenAPI 规范与生成器版本在项目骨架阶段锁定 | 对 Web、App、小程序和第三方保持稳定契约；先不引入 GraphQL 复杂度。 |
| 身份认证 | Laravel Sanctum | 与 Laravel 13 兼容的受支持版本，随框架依赖锁定 | 自有一方客户端和 SPA/API 的简单令牌/会话场景足够；若需要第三方授权委托，再评估 OAuth 2.0。 |
| 文件存储 | S3 兼容对象存储 + CDN | 不绑定单一云厂商版本；S3 API 与 SDK 版本按所选服务兼容矩阵锁定 | 文件不进关系库；保存对象键、元数据，私有对象走短期签名链接。 |
| 搜索 | 初期 MySQL 查询；需要时评估 Meilisearch / OpenSearch | 初期不增加搜索服务；启用后选受支持稳定版并记录索引重建流程 | 搜索是可重建读模型，不是商品、价格、库存的事实来源。先用真实数据衡量搜索体验与负载。 |
| 前端 | 消费端独立 API；后台 Filament | 本阶段不选定独立前端框架；后续按 SEO、SSR、团队经验比较 Nuxt 3 与 Next.js | 不把未确认的前端框架加入当前依赖面；小程序/App 也消费同一版 API 契约。 |
| 测试与质量 | Pest、Pint、Larastan/PHPStan | 与 PHP/Laravel 13 兼容的受支持稳定版；提交依赖锁文件 | 自动化守住格式、类型、业务规则和回归；CI 必须可重复执行。 |
| 架构 | 模块化单体 | 不绑定额外 DDD 框架；按业务增长演进 | 订单、库存、支付、分销有边界但初期可共享事务数据库；避免过早微服务和不必要抽象。 |

**明确的版本锁定规则**

1. Laravel 主版本基线为 **13**。PHP 的最低基线为 **8.4.3**（CVE-2024-4577 修复下限，与 `composer.json` `^8.4.3` 一致）；生产部署使用 PHP 8.4 分支最新安全补丁版，不得使用 8.4.0–8.4.2 或 8.3。
2. Filament、Horizon、Sanctum 和质量工具的精确版本以官方兼容矩阵与 Composer 解析结果为准。当前仓库还没有 `composer.json` / `composer.lock`，所以不把未经实际解析验证的主版本号伪装成已确认事实。
3. 主数据库选择 **MySQL 8.4 LTS**。版本补丁由托管服务/容器镜像及时更新；测试和生产使用同一主版本系列。
4. Redis 先确认 Laravel 客户端、队列配置、托管服务和部署镜像互相支持，再锁定稳定受维护版本。不要只根据 `latest` 标签部署。
5. 精确版本通过 `composer.lock`、容器镜像摘要或部署 IaC 固定；自动化依赖更新通过 CI、测试、迁移评估后合并。安全修复不因版本锁定而长期搁置。
6. 主要版本升级要有单独升级 PR：查官方升级指南，先升级 CI 与测试环境，检查插件兼容、弃用项、迁移和回滚方案。

### 1.3 关键架构决定

- 多租户先采用共享数据库/共享表及显式 `tenant_id`，所有入口、队列、缓存键、导出和后台操作都执行租户授权；建立跨租户访问失败测试。
- 订单、库存、支付是高一致性边界。金额使用最小货币单位整数加币种；库存流水、支付和订单快照保留审计事实；外部副作用用幂等键、事务 Outbox 和可重试队列。
- Filament 是管理端交互层，授权仍由 Policy/领域应用服务保障；API 与后台不得分别复制业务规则。
- 搜索、缓存、分析是可重建读侧，不作为订单、价格、库存的主数据源。
- 初期选一个主数据库和一套可重复部署方式；只有真实指标或隔离/法规要求证明必要时才增加数据库、搜索服务或微服务。

## 2. 语言与运行时（分）

### 2.1 PHP 版本比较

| 版本 | 优点 | 风险/成本 | 本项目判断 |
| --- | --- | --- | --- |
| PHP 8.2 | 部署面广，历史依赖兼容性常较好 | 生命周期与新框架兼容窗口有限，作为新项目基线会缩短维护余量 | 不作为本项目运行时；最低基线为 8.4.3。 |
| PHP 8.3 | 生态成熟、部署可得 | 生命周期比更新分支更短；部分依赖可能逐步优先支持新版本；PHP-CGI 参数注入 CVE-2024-4577 等 8.4 修复不覆盖该分支 | **已不作为本项目运行时**（早期决策，已被 8.4.3 基线取代，见 `docs/architecture/architecture-components.md` 与 `composer.json`）；历史项目或遗留扩展场景可单独评估。 |
| PHP 8.4 | 新项目较新的稳定运行时，语言与运行时改进较多 | 扩展、监控代理、少数依赖和托管镜像支持程度需逐项确认 | **最低基线 8.4.3，优先部署运行时**（生产用 8.4 最新安全补丁版）。完成全依赖、扩展、Pest、静态分析和压测验证后采用。 |
| PHP 更新的后续主版本 | 可获得后续性能、语言改进 | 生态成熟和框架兼容需要验证；过早采用增加生产故障面 | 不追逐最新版本；达到框架、扩展和生产工具支持条件后再评估。 |

### 2.2 Laravel 版本比较

| 选择 | 适用性 | 结论 |
| --- | --- | --- |
| Laravel 11/12 等旧主版本 | 对存量项目或被特定依赖约束的系统有意义 | 本仓库目标已明确为 Laravel 13；新建骨架不回退旧版，除非 13 的关键依赖或部署平台尚未支持并形成明确 ADR。 |
| Laravel 13 | 新项目基线；现代 Laravel 生态与当前目标一致 | **当前选择**。安装前检查 PHP 最低版本、支持周期、升级指南以及 Filament/插件兼容。 |
| 未来 Laravel 主版本 | 可在其稳定发布且生态兼容后升级 | 不因“最新”自动升级；通过独立升级评审，确保测试、迁移与回滚准备充分。 |

**为什么不追求旧版最大兼容性：**这是新建 SaaS 参考实现，没有既有生产代码包袱；较新的受支持框架能获得更长维护窗口。但新版本只有在 Filament、支付 SDK 和部署扩展兼容后才真正有价值。

## 3. 管理后台：Filament（分）

### 3.1 横向比较

| 方案 | 优势 | 代价 | 结论 |
| --- | --- | --- | --- |
| Filament | Laravel 原生体验好，Resource、表单、表格和面板可快速搭建；适合内部运营和商家后台 | 主版本需要跟随 Laravel/PHP 兼容；复杂流程仍需自定义页面/用例；不能把 UI 能见性当权限 | **选择**：快速形成一致的管理端，配合 Policy、租户上下文和应用用例。 |
| Livewire 自建管理端 | 与 Laravel 集成，可完全控制交互 | 大量列表/表单/权限/导出功能需自建维护 | 适用于后台交互高度定制且团队有维护能力时，不作为起步方案。 |
| Vue/React 独立后台 | 前后端分离明确，复杂交互与前端团队协作灵活 | 多一套构建、状态、鉴权与部署体系；重复实现常规 CRUD | 若后台将来需要独立产品化或复杂工作台，再作专项评估。 |

### 3.2 Filament 版本选择

Filament 的主版本必须与 Laravel 13、PHP 版本及插件矩阵核对。当前仓库尚未引入 Composer 依赖，因此此处结论是“采用兼容 Laravel 13 的受支持稳定主版本”，不是已经锁定一个具体数字。初始化时执行依赖解析、安装官方当前稳定版，提交 `composer.lock`，并验证两个 Panel、权限插件（若有）、表单/表格及升级路径。避免在生产项目中跨 Filament 主版本自动升级。

平台运营 Panel 与商家租户 Panel 可共用业务用例，但需使用不同的认证/授权策略、导航和跨租户权限；任何敏感写操作都必须在服务端授权。

## 4. 数据层：MySQL 与 Redis（分）

### 4.1 MySQL / PostgreSQL 横向比较

| 维度 | MySQL 8.4 LTS | PostgreSQL（受支持稳定主版本） |
| --- | --- | --- |
| 事务与约束 | 事务、行锁、索引和约束足以支撑典型订单/库存事务；需正确设计隔离和索引 | 事务、约束、复杂查询能力强；丰富数据类型和 SQL 特性 |
| 生态与部署 | Laravel 常见生产选择，托管服务和运维人才普遍 | Laravel 支持成熟，复杂查询/数据建模需求场景有优势 |
| 迁移与运维 | 团队需要具备 InnoDB、备份恢复、主从与索引运维能力 | 团队需要具备 VACUUM、索引维护、备份恢复与连接池等运维能力 |
| 风险 | 不同 SQL 方言/JSON 行为需留心；不可依赖宽松 SQL 模式 | 迁移成本、团队运维熟悉度和托管环境需考量 |
| 项目决定 | **默认选择 8.4 LTS**，一套生产与测试标准 | 可作为替代方案，但若改选，需要在项目早期决定并把 CI/迁移/运维都统一到 PostgreSQL；不要同时支持两套数据库作为目标。 |

**选择 MySQL 的理由：**电商基础实体和强事务工作负载由 MySQL 足以覆盖；团队和托管环境通常容易获得支持；以单一数据库为基线能减少迁移分支。若团队已具备更强 PostgreSQL 经验，或有明确的数据查询/扩展需求，可以通过 ADR 重新评估，而不是为“通用”同时维护两套。

### 4.2 MySQL 版本比较

| 版本策略 | 评估 | 结论 |
| --- | --- | --- |
| MySQL 8.0 系列 | 部署普及，现存系统适配范围大 | 对新项目需额外关注生命周期和维护窗口；不优先于 LTS 新基线。 |
| MySQL 8.4 LTS | LTS 维护路线明确，适合长期稳定运行；主版本适配需在 CI 中验证 | **选择**。应用、迁移、测试库和部署环境统一到 8.4 系列。 |
| 创新/更新的非 LTS 系列 | 可更早获得新能力 | 新 SaaS 不需要承担非 LTS 跟进节奏；仅在特定需求经测试证明必要时考虑。 |

部署时固定具体受支持补丁或托管服务维护版本，开启严格 SQL 模式，核实字符集/排序规则、时区、备份恢复与连接数；不把版本标签 `latest` 用于生产。

### 4.3 Redis 与数据库职责

| 方案 | 优势 | 风险/适用范围 | 结论 |
| --- | --- | --- | --- |
| Redis | 低延迟缓存、Laravel Queue、限流计数和短期协调数据；Horizon 监控 Redis 队列 | 内存成本、持久化/高可用要设计；不能用缓存值替代库存账本或支付事实 | **选择用于缓存和队列**；精确服务版本按 Laravel 客户端及托管支持情况锁定。 |
| 仅数据库队列 | 部署简单，初期组件少 | 高吞吐/队列可观测性和吞吐隔离能力较弱 | 本地或极早期可用；正式环境按需要转 Redis Queue，不把数据库队列误作业务事务队列保证。 |
| RabbitMQ / Kafka | 适合复杂路由、跨服务事件流或高吞吐事件平台 | 运维复杂且现阶段没有多服务/流处理需求 | 暂不引入。出现明确事件流/集成需求、团队运维能力后再评估。 |

Redis 的具体大版本不在没有测试的情况下预设。项目初始化时确认 Redis 服务端版本、Laravel 所用客户端（PhpRedis 或 Predis）、Horizon 和托管服务兼容；统一连接配置、密码/TLS、持久化与高可用策略。库存预占必须通过数据库事务和约束形成正确性基础。

**CI/集成验证基线（服务镜像）**：当前 CI 使用 `mysql:8.4` 与 `redis:8`（`.github/workflows/ci.yml` services 段）。本行为 CI 与集成验证的版本登记处；CI 或部署镜像的 tag 变更时，须在同一次 PR 中同步更新本文 §1.2 表与本章对应行（AGENTS.md 组件决策单一出处约定）。

## 5. API、认证与异步任务（分）

### 5.1 REST 与 GraphQL

| 方案 | 适合场景 | 选择 |
| --- | --- | --- |
| REST + OpenAPI | 业务资源明确，多终端复用，便于缓存、审计和第三方接入 | **选择 `/api/v1`**。统一分页、错误结构、限流、请求 ID 与弃用策略。 |
| GraphQL | 客户端字段组合复杂、多个数据源聚合，且团队愿意治理 schema、授权、缓存和查询成本 | 暂不引入；不能仅为“前后端分离”而增加。 |

API 版本是契约版本，不等同于 Laravel 版本。保持兼容性；不兼容改动发布新 API 版本并留弃用窗口。

### 5.2 Sanctum 与 OAuth 2.0

| 方案 | 优势 | 限制 | 结论 |
| --- | --- | --- | --- |
| Sanctum | 与 Laravel 集成简单，适用于自有 SPA、移动端令牌等第一方应用 | 不是完整 OAuth 授权服务器；第三方应用授权委托需更完整协议能力 | **当前选择**，降低一方客户端的认证复杂度。 |
| OAuth 2.0 / OpenID Connect | 标准化第三方授权、多客户端委托和身份联合能力 | 授权服务器配置、令牌生命周期、密钥管理和威胁模型更复杂 | 当 SaaS 需要外部开发者授权、SSO 或标准委托时再引入；按场景选择成熟实现，不自造协议。 |

无论选哪种，授权都必须结合租户成员关系和服务端 Policy。令牌不能替代对象级授权，密钥与令牌不可写入日志。

### 5.3 Redis Queue、Horizon 与 Outbox

Laravel Queue/Horizon 适合应用内的后台工作、邮件、图片处理和异步集成。Horizon 是队列运维界面，不是可靠事件交付的替代品。订单数据库事务同时写 `outbox_messages`；提交后 worker 发布，消费者使用幂等键，失败有重试上限、告警、死信/重放及对账。支付请求不能放在数据库长事务中。

## 6. 文件、搜索与消费者前端（分）

### 6.1 对象存储

关系数据库适合交易元数据，不适合持久存放商品图片/文件二进制。采用 S3 兼容对象存储以获得弹性、生命周期策略和 CDN 集成；数据库保存对象键、大小、类型、校验和等必要元数据。供应商选择关注区域、合规、出网费、生命周期、版本化、私有签名 URL 和恢复策略，不以“兼容 S3”推断所有高级功能完全一致。

### 6.2 搜索引擎

| 方案 | 优势 | 代价 | 采用时机 |
| --- | --- | --- | --- |
| MySQL 查询 | 架构简单、商品数据即时一致、无需同步索引 | 复杂相关性、拼写纠错、分面筛选能力有限 | **初期选择**，先量化商品规模、延迟和搜索质量。 |
| Meilisearch | 搜索集成与运维相对轻量，适合常见站内搜索 | 独立索引与同步链路；能力及规模需按实际负载验证 | 中小规模搜索体验成为瓶颈时评估。 |
| OpenSearch | 搜索、聚合和规模化能力丰富，生态较广 | 集群成本、调优、升级和索引治理更复杂 | 大规模、多维聚合或已有运维平台时评估。 |

任何搜索引擎都是可重建索引。通过 Outbox/队列同步并设计全量重建，商品、价格和库存仍以主数据库及明确的库存服务为权威来源。

### 6.3 店铺前端选择

当前先定义稳定 REST API，前端框架不作为当前基线依赖。若要构建 SEO/SSR 电商 Web，比较 Nuxt 3（Vue 生态）与 Next.js（React 生态）的团队能力、SSR/缓存策略、部署平台、支付跳转和多租户域名管理后单独决策。Filament 专注运营/商家后台；小程序和 App 复用 API 契约。

## 7. 测试、代码规范与部署（分）

### 7.1 质量工具比较

| 工具/方案 | 作用 | 选择理由与注意点 |
| --- | --- | --- |
| Pest | PHP 测试框架，提供简洁测试表达 | 选择为测试编写体验；业务断言仍要覆盖事务、租户边界和并发语义。 |
| PHPUnit | PHP 主流测试底层/框架，生态广 | Pest 与 PHPUnit 生态关联；不要把二者当作互斥的测试能力，CI 以项目实际安装配置运行。 |
| Laravel Pint | PHP 风格格式检查/修复 | 采用自动格式化，避免团队风格争议。 |
| PHPStan / Larastan | 静态类型与 Laravel 项目分析 | 采用并逐步提高严格度；基线必须审查，不应无限增长忽略规则。 |
| PHP_CodeSniffer 等 | 可做风格或规则校验 | 当前 Pint 已能满足格式统一；只在明确规范缺口时增加工具。 |

测试至少包含租户越权拒绝、重复下单幂等、库存并发预占/释放、重复/乱序支付回调、退款冲回、迁移和队列重试。生产部署配置必须具备备份与恢复演练、结构化日志、错误告警、队列监控、健康检查与密钥管理。

### 7.2 版本/升级管理

- PHP、Composer 包和容器基础镜像均固定可复现版本；生产镜像建议再固定摘要。
- 每周/按维护节奏检查安全公告和依赖更新；安全升级优先级高于普通功能升级。
- 升级 PR 需运行格式、静态分析、单元/Feature 测试、迁移检查；涉及 Laravel/Filament 主版本时额外做后台流程回归。
- 数据库迁移遵循 expand-and-contract：先兼容地加结构/双读写，发布应用后再移除旧结构，避免应用回滚时数据不可读。

## 8. 风险、待确认项与复核触发条件

### 待确认（骨架初始化前）

1. 用实际 Composer 解析结果确定 Laravel 13 兼容的 Filament、Horizon、Sanctum、Pest、Pint、Larastan 版本，保存 `composer.lock`。
2. 验证 PHP 8.4 下所有 PHP 扩展、支付 SDK、监控/安全代理兼容；不兼容时须在 PR/ADR 中说明，不得回退 8.3 基线（最低基线固定为 8.4.3）。
3. 结合目标云服务确定 MySQL 8.4 LTS 补丁线、Redis 服务版本、备份恢复、TLS 与可用区方案。
4. 明确首批支付渠道、运营地区与币种、税费/发票责任、个人信息保留策略；这些决定影响支付、订单和审计模型。
5. 确认消费者端是否要求 SEO/SSR、首发终端和团队前端技能，再选择 Nuxt/Next 或小程序方案。

### 触发复核

- 官方安全支持窗口、框架兼容矩阵或托管服务支持变化；
- 新租户法规/数据驻留要求导致共享表隔离不满足；
- 搜索、数据库、队列的实际指标突破目标 SLO；
- SaaS 开放第三方应用授权或引入跨服务事件平台；
- MySQL 运维经验、托管能力或业务查询需求发生改变。

每次改变主选型，新增/更新 ADR，记录背景、备选方案、决策、风险与迁移计划，避免只改 README 而丢失决策依据。
