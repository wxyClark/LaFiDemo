## 3. 使用顺序评估（全流程走一遍）

> 仓库现实假设（来自 `architecture-review.md` 背景知识）：单开发者 + AI 协作、main 分支受保护（CI 必绿 + 严格分支最新性）、CI 约 2 分钟。

### 3.1 逐阶段映射

| workflow 阶段 | 该阶段应调用模板 | 当前库给出的顺序 | 与实际使用顺序是否一致 | 跳步/倒序风险 |
|:-----------:|:---------------:|:---------------:|:-------------------:|:------------:|
| 0（准备上下文） | 0 | 0 | ✅ 一致 | 无 |
| 1（需求分析） | 1 | 1 | ✅ 一致 | 无 |
| 2（PRD） | 2 | 2 | ✅ 一致 | 无 |
| 3（架构设计） | 3 | 3 | ✅ 一致 | 无 |
| 4（方法评审） | 4 → 5（→ 9 辅助） | 4 → 5 → 9 | ⚠️ 部分一致 | 模板 9 排在 8 之后，用户可能误认为"先测试再安全审查"；设计阶段应用 9 时顺序倒置 |
| 5（任务拆分） | 6 | 6 | ✅ 一致 | 无 |
| 6（编码） | 7 | 7 | ✅ 一致 | 无 |
| 7（自动化测试） | 8 | 8 | ✅ 一致 | 无 |
| 8（PR 与人工审查） | 10（→ 9 深度审查） | 9 → 10 | ⚠️ 部分一致 | 模板 9 排在 10 之前，暗示"安全审查先于 PR 描述"；但实际工作流中 9 也可在 PR 之后补做，顺序不强制 |
| 9（CI/CD 发布） | 11 | 11 | ✅ 一致 | 无 |
| 10（上线验收复盘） | 12 | 12 | ✅ 一致 | 无 |

**关键跳步风险：模板 0（任务分流）的"本轮模式"选项（`prompt-library.md:11`）为"只读分析 / 编写 PRD / 设计评审 / 执行已批准的实现"，缺少"需求分析"和"安全审查"两个独立入口。若用户按此选项分流，需求分析（模板 1）和安全审查（模板 9）的入口被隐藏，导致跳步或走错分支。**

### 3.2 过重/过轻评估（结合单开发者 + 2 分钟 CI 现实）

| 模板 | 过重/过轻 | 理由 |
|:---:|:--------:|------|
| 0（任务分流） | ⚠️ 过重 | 要求 AI"检查仓库实际代码、依赖锁文件、已有测试和当前分支"，对 2 分钟 CI 的快速迭代场景偏重；可简化为"读 AGENTS.md + 任务描述"即可分流 |
| 3（架构设计） | ⚠️ 偏重 | 要求 9 项输出（含时序图、状态机、索引草图、Outbox 设计等），对低风险单开发者改动过重；应按 `workflow.md:150-154` 风险分级裁剪 |
| 4（反向评审） | 适中 | 与 2 分钟 CI 节奏匹配；但"不得自我批准"在单开发者场景下意味着必须人工介入，是合理的质量底线 |
| 5（ADR 起草） | 偏轻 | 无验收输出定义（ADR 何时算"完成"）；`delivery-and-operations.md:16` 要求"背景、备选、决策、后果及复核条件"，模板 5 已覆盖但无明确完成判定 |
| 7（编码） | 适中 | 与 2 分钟 CI 匹配；"先给简短实现计划"符合小步提交原则 |
| 8（Pest 测试） | 适中 | 要求"运行实际可行的测试并报告命令、环境和结果"，与 `architecture-review.md` R-02（SQLite vs MySQL 差异）结合时需特别注意测试引擎 |
| 9（安全审查） | 偏轻 | 无明确完成判定（"阻断项解决"还是"全部修复"）；对高风险领域（支付/库存/租户）应强制完成，但模板 9 未区分风险等级 |
| 11（CI/CD 发布） | 偏轻 | 对 2 分钟 CI 的快速发布场景，四段操作清单（Pre/Deploy/Post/Rollback）可能过重；可简化为"CI 绿 + 回滚方案确认" |
