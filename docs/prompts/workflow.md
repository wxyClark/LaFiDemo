# 推荐开发全流程

## 1. 角色与责任边界

AI 是开发协作工具，不是需求、架构、安全、合并或生产发布的最终责任人。推荐明确以下责任：

- **产品负责人/需求方**：确认目标用户、业务规则、范围、验收口径、优先级及非目标。
- **架构/技术负责人**：确认领域边界、数据模型、接口契约、可靠性、安全、兼容性及迁移方案。
- **开发者**：实现、测试、review、文档同步，确认代码与业务意图一致。
- **Reviewer/发布负责人**：审查高风险变更、CI 结果、上线窗口、回滚与监控。
- **AI 助手**：根据仓库上下文分析、提出问题、起草文档/代码/测试、解释差异；不得虚构已执行操作或代替人工审批。

小型改动可合并相邻阶段，但不能跳过验收标准、测试和审查。支付、库存、退款、租户隔离、权限、个人信息和生产迁移应保留完整门禁。

## 2. 全流程总览

| 阶段 | 主要输入 | 交付物 | 放行条件 |
| --- | --- | --- | --- |
| 0. 准备上下文 | Issue/需求、代码仓库 | 仓库事实、未知问题、影响范围 | 已阅读 `AGENTS.md` 和相关规则；需求边界清晰 |
| 1. 需求分析 | 用户问题、业务背景 | 用户/问题、流程、约束、风险、澄清问题 | 关键业务规则有负责人确认；假设显式 |
| 2. PRD | 已澄清需求 | PRD、验收标准、范围与非目标 | 验收可测试、异常流程和权限考虑齐全 |
| 3. 架构/领域设计 | 批准 PRD、现有架构 | 模块影响、流程图、数据/API 变更、非功能设计 | 与模块化单体及技术基线一致；高风险流程有一致性方案 |
| 4. 方法评审 | 设计稿、备选方案 | Review 意见、ADR、风险与决议 | 阻断项解决；责任人批准不可逆/高风险决定 |
| 5. 任务拆分与分支 | PRD、通过的设计 | 小任务、依赖顺序、feature 分支 | 范围可审查，每项有验收/测试定义 |
| 6. 编码 | 任务、设计、仓库代码 | 最小代码变更、迁移、文档 | 不变量和授权在服务端落实；无未批准范围扩张 |
| 7. 自动化测试 | 实现和验收标准 | Pest 测试、质量/安全检查结果 | 关键路径通过；实际命令和未跑项如实报告 |
| 8. PR / 人工 Review | 分支变更、CI | PR 描述、审查与修复记录 | 必需 reviewer 批准，阻断意见解决，CI 绿灯 |
| 9. CI/CD 与发布 | 已批准 PR、制品 | 可追溯制品、部署记录、回滚方案 | 预发布/发布检查通过，监控和负责人就绪 |
| 10. 线上观测/复盘 | 发布结果、指标 | 验收记录、事故/改进项、文档更新 | 业务指标正常；问题有责任人与后续期限 |

## 3. 阶段细则与提示词目标

### 阶段 0：准备上下文和仓库事实

先读取根目录 `AGENTS.md`，相关 `docs/rules/` 和架构文档，并检查实际实现、依赖锁文件、测试脚本和 Git 状态。AI 先报告发现，不要在分析阶段擅自改动。

**目标提示词应要求：**
- 说明要解决什么、用户是谁、现有代码在哪、可能影响哪些模块。
- 区分仓库事实、用户提供信息、推断和未知项。
- 给出需要澄清的问题，不因问题缺失自行发明需求。
- 说明当前工作区或分支是否有未提交变更（工具可见时）。

**放行：**确认相关上下文完整，关键未知项已由需求方回答或作为明确假设批准。

### 阶段 1：需求分析

按用户旅程梳理触发条件、主流程、失败/取消/重试流程、角色权限、租户归属和数据生命周期。电商场景检查在线交易、门店 O2O、渠道、库存分配、售后、分销及财务影响是否相关。

**输出：**问题陈述、用户/角色、当前与目标流程、业务规则、边界/非目标、依赖、异常路径、数据敏感级别、指标、待确认问题。

**放行：**产品/需求负责人确认目标和业务规则，尤其是价格口径、状态转换、库存与退款策略等不能由 AI 猜测的事项。

### 阶段 2：PRD 与验收标准

PRD 不要直接写成实现方案。描述用户可见行为和业务结果，明确权限、状态、失败场景、兼容性和埋点/审计要求。每条验收标准使用可验证语言，优先 Given/When/Then。

**输出：**背景/目标、用户故事、主流程、异常与边界、权限和租户范围、验收标准、非功能要求（性能/可靠性/安全/可访问性）、埋点、上线策略、范围和非目标、未决事项。

**放行：**验收条件可独立测试，非功能要求有度量或明确解释，负责人批准范围。

### 阶段 3：架构与领域设计

根据批准的 PRD 追踪变更到已有模块，不默认新增模块或服务。定义模块公开接口、数据所有权、实体/状态机、事务边界、并发模型、租户授权、幂等、事件/Outbox、API、迁移、缓存、观测和回滚影响。

**输出：**上下文/时序或状态图、模块影响、数据表/索引草图、API/事件契约、事务与失败处理、威胁/隐私分析、测试策略、迁移发布方案、备选项。

**放行：**订单/支付/库存等一致性决策明确；方案与 `docs/architecture/architecture.md`、`docs/architecture-blueprint.md`、`docs/technology-selection.md` 不冲突，或有 ADR 解释变更。

### 阶段 4：方法评审 / ADR

进行至少一轮反向审查：让 AI 或 reviewer 专门找错误假设、遗漏权限、跨租户访问、竞态、重放、重复执行、扩展和回滚风险。AI 的方案不能自我批准。

**需检查：**
- 需求是否过度实现/遗漏异常流程？
- 多租户边界是否覆盖 API、Filament、队列、导出、缓存、Webhook？
- 数据约束、唯一键、索引、状态机和幂等键是否能保护不变量？
- 数据库事务是否短？外部网络调用是否在事务外？
- 重试、乱序/重复回调、Outbox 消费和补偿是否安全？
- 迁移对旧应用、回滚和历史数据是否兼容？
- 日志、审计、错误响应是否会泄露敏感信息？

**输出：**阻断/非阻断评论、修订方案、ADR（背景、备选、决定、后果、复核条件）。

**放行：**阻断意见解决，责任人明确批准关键业务/架构取舍。

### 阶段 5：实施计划与分支管理

将工作拆成小 PR 可承载的垂直切片，每个任务都带有修改范围、验收标准、测试和依赖。跨多个 PR 的数据库/接口变更说明先后顺序及兼容窗口。

**分支建议：**
- `main`：受保护，可部署的主干；禁止直接提交。必须通过 CI 和所需 review。
- `feature/<issue>-<short-name>`：需求功能；小改动可使用 `fix/<issue>-<short-name>`。
- `hotfix/<issue>-<short-name>`：生产紧急修复，仍需最少化 review、测试、审计和回合并主干。
- 使用短生命周期分支，定期同步主干；不长期维护与主干漂移的集成分支。
- PR 以 squash 或团队统一策略合并；提交说明清晰。分支保护、必需状态检查和审批人数按团队权限配置，文档不能替代 GitHub 实际设置。

**放行：**任务粒度可在一个 PR 中解释和验证；分支名/Issue 对应，迁移顺序明确。

### 阶段 6：AI 辅助编码

每次仅让 AI 完成已批准任务中的一小段。编码前给出计划和文件范围；编码后展示 diff 摘要、关键风险和未解决问题。优先修改既有模式，不复制粘贴出第二套业务逻辑。

**编码约束：**遵守 `AGENTS.md` 和 `docs/rules/`；依赖存在才使用；权限/租户检查落在服务端；业务副作用幂等；迁移可重建；文档保持同步。AI 不得自行修改 CI 安全门禁、删除测试、放宽授权或关闭扫描来让构建变绿。

**放行：**diff 与计划一致，人工检查需求覆盖、异常处理、代码风格、敏感字段和数据影响。

### 阶段 7：自动化测试与质量验证

按验收标准从外向内测试：API/Filament 权限与行为、应用用例和数据库结果、领域纯逻辑。并发和 MySQL 专属约束必须在真实 MySQL 版本系列验证；涉及 Redis 队列的行为在适当 CI 环境集成验证。

**建议门禁（根据已安装项目脚本执行）：**
1. 依赖/锁文件验证与安全审计；
2. Pint 格式检查；
3. Larastan/PHPStan；
4. 相关 Pest Unit/Feature/Integration 测试；
5. MySQL migration fresh/seed 与升级路径验证；
6. 有条件时做依赖扫描、Secret 扫描、SAST 和关键业务并发测试。

每项报告精确命令、退出结果、环境/数据库版本。没有实际运行的项标为“未运行”及原因，不可虚报。

**放行：**关键验收与回归测试通过；任何失败均修复或有批准的、可追踪的豁免和期限。

### 阶段 8：PR 与人工审查

PR 描述包含问题、方案、影响模块、API/Schema 变化、租户/权限影响、事务与幂等、测试结果、迁移/发布顺序、风险和回滚。AI 可生成审查清单或找 bug，但作者与 reviewer 对结论负责。

**强制专门审查：**租户隔离、认证授权、支付/退款、库存/订单状态、个人信息、生产密钥或破坏性迁移。处理所有实质性意见后再合并。

**放行：**CI 必需检查绿灯、所需 Review 已批准、冲突解决、文档和迁移齐备。

### 阶段 9：CI/CD、发布与分支策略

CI 在 PR 运行质量门禁；主干合并后生成可追溯构建制品并部署到预发布环境。生产发布应由授权人员/受控工作流批准，不能把 AI 自动编码权限等同于生产发布权限。

**部署检查：**
- 制品关联 commit、依赖锁和镜像摘要；secret 从安全配置注入。
- 迁移遵循 expand-and-contract，先确认应用版本兼容、备份和回滚；不盲目自动 rollback 数据库。
- Queue worker/Horizon 平滑重启，确认旧 Job 可被新代码处理。
- 采用分批/灰度或可控发布，观察错误率、延迟、队列积压、支付成功率、库存异常与 Outbox 延迟。
- 回滚和暂停扩量条件明确；数据库不可逆变更前需单独审批和恢复验证。

**放行：**负责人确认发布窗口、观测、客服/运营通知和回滚责任人已就绪。

### 阶段 10：上线验收与复盘

对照 PRD 验收标准验证真实环境行为，不在日志中暴露客户敏感数据。记录发布时间、制品版本、变更、指标及未完成项。故障复盘输出系统改进、责任人与期限，不仅归因于个人或 AI。

## 4. 需求风险分级

| 级别 | 示例 | AI 使用方式 |
| --- | --- | --- |
| 低 | 文案、无副作用展示、内部小型重构 | 可在明确范围内直接草拟/实现，仍需测试与 review。 |
| 中 | 商品管理、筛选、普通后台流程、非关键报表 | 先分析方案，再分步骤实现；验证租户和权限。 |
| 高 | 下单、价格、优惠、库存、支付、退款、分销账务、租户权限、个人信息、生产迁移 | 先产出 PRD/设计/威胁与失败分析，经人批准后编码；要求专门 review、关键集成/并发测试和上线回滚审查。 |

## 5. 交付完成定义（Definition of Done）

- 已满足批准 PRD 的验收标准，明确列出未实现项。
- 服务端验证、授权和租户隔离具备测试；关键业务不变量和重复执行具备测试。
- 迁移、API 文档、运维/配置说明按需更新；无秘密、生产数据或敏感 payload 泄露。
- 按实际项目配置执行质量门禁；未执行项如实说明。
- PR Review 和 CI 满足仓库保护规则；上线具备监控、回滚/补偿和负责人。
- AI 生成代码经人工审阅，不因生成速度而跳过领域、安全、许可证及依赖检查。
