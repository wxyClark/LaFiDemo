# AI 提示词模板库

使用时将方括号内容替换为本次信息。每个提示词都应要求 AI 遵循仓库 `AGENTS.md` 和 `docs/rules/`，区分已知事实、推断和未知项，并准确报告未执行的操作。不要把全部模板一次性串成无人审查的自动代理链。

## 使用顺序

模板编号与 `workflow.md` 阶段门（阶段 0-10）对应；按阶段顺序使用，缺步须先补齐前置阶段。

| 模板 | 名称 | 对应 workflow 阶段门 |
|:---:|------|:-------------------:|
| 0 | 仓库上下文与任务分流 | 阶段 0 准备上下文 |
| 1 | 需求分析与澄清 | 阶段 1 需求分析 |
| 2 | PRD 起草 | 阶段 2 PRD |
| 3 | 架构与技术设计 | 阶段 3 架构设计 |
| 4 | 架构/方法反向评审 | 阶段 4 方法评审（前半） |
| 5 | ADR 起草 | 阶段 4 方法评审（后半，评审产出） |
| 6 | 拆分任务与分支计划 | 阶段 5 任务拆分与分支 |
| 7 | 编码实现 | 阶段 6 编码 |
| 8 | Pest 测试设计/补齐 | 阶段 7 自动化测试 |
| 9 | 安全与隐私审查 | 阶段 4（辅助）/ 阶段 8（主要） |
| 10 | PR 描述与代码 Review | 阶段 8 PR 与人工审查 |
| 11 | CI/CD 与发布检查 | 阶段 9 CI/CD 发布 |
| 12 | 上线后验收与复盘 | 阶段 10 上线验收复盘 |

- 模板 4 与 5 同属阶段 4：先反向评审（4），后 ADR 起草（5），ADR 是评审产出之一，无独立阶段门。
- 模板 9 可在阶段 4（设计阶段安全/隐私威胁分析）或阶段 8（PR 深度审查）使用；设计层面快速扫描用模板 4，深度威胁审查用模板 9。
- 模板 7（编码）前必须先完成模板 6（任务拆分与分支计划）。
- 需求风险分级见 `workflow.md` 第 4 节：低风险可裁剪模板 3/4/9，高风险（下单、价格、库存、支付、退款、租户权限、个人信息、生产迁移）须走全流程。

## 0. 仓库上下文与任务分流

```text
你是 LaFiDemo 的资深 Laravel 电商 SaaS 工程师。开始前先阅读根目录 AGENTS.md，以及与本任务相关的 docs/rules/、docs/architecture/architecture.md、docs/architecture-blueprint.md、docs/technology-selection.md。检查仓库实际代码、依赖锁文件、已有测试和当前分支，不要假设文档描述的功能已经实现。

任务：[粘贴需求/Issue]
本轮模式：[只读分析 / 编写 PRD / 设计评审 / 执行已批准的实现]

请先输出：
1. 仓库事实（附文件路径/符号，区分已实现与规划）；
2. 用户目标、受影响模块和数据；
3. 已知事实、推断、假设、未知项；
4. 需要我回答的阻断问题；
5. 建议下一阶段及其可审查交付物。

除非模式明确要求实现，本轮不要修改文件。不要编造命令结果、依赖版本或外部官方结论。
```

## 1. 需求分析与澄清

```text
请对以下需求做业务需求分析，不要直接写代码或把技术方案冒充需求。
需求：[粘贴]
业务背景/目标用户：[填写]
已知约束：[运营地区、渠道、角色、上线时间等]

请输出：
- 问题陈述、目标用户/角色、现状与期望结果；
- 主用户旅程与业务规则；
- 成功、失败、取消、重试、超时、重复操作等边界流程；
- 租户/门店/渠道/用户权限及数据归属；
- 对价格、库存、订单、支付、退款、促销/分销账务的影响（不适用也说明）；
- 隐私、安全、审计、性能与运营约束；
- 范围内、范围外、依赖、风险；
- 按“阻断/重要/可后续”排序的澄清问题。

明确区分需求事实与假设。涉及金额口径、状态机、库存预占/释放、支付竞态或佣金规则时不得自行决定；列出需要业务负责人确认的选项。
```

## 2. PRD 起草

```text
根据已确认的需求分析起草 PRD。确认内容：[粘贴答复/决议]。读者包括产品、开发、测试、运营。

PRD 必须包含：背景与问题、目标/非目标、用户与权限、前置条件、主流程、异常/边界流程、业务规则、数据/审计/隐私要求、非功能要求、埋点/运营、兼容性、发布策略、依赖和风险。

把验收标准写成可执行、无歧义的 Given/When/Then 或等价清单，覆盖正向、拒绝/越权、重复请求、失败与恢复。标识无法从当前信息确定的内容为 TBD，并注明负责人，不要补造规则。不要写实现代码；最后给出 PRD Review 清单和待批准项。
```

## 3. 架构与技术设计

```text
基于已批准 PRD 设计 LaFiDemo 的实现方案。
PRD/Issue：[链接或内容]
必须遵守：AGENTS.md、docs/rules/、docs/architecture/architecture.md、docs/architecture-blueprint.md、docs/technology-selection.md。

先检查仓库现有模块和实现。请提供：
1. 需求到模块/入口的映射，数据所有权和模块依赖方向；
2. 请求/任务时序图及关键状态机；
3. 表/字段/唯一键/外键/索引变更建议和数据保留；
4. API、事件、Job 或 Filament Action 的契约草图；
5. 租户授权、认证、幂等、事务、并发、Outbox、失败重试/补偿设计；
6. 安全、隐私、日志与审计影响；
7. 迁移兼容、发布次序和回滚/恢复方案；
8. Unit/Feature/Integration/并发测试矩阵；
9. 备选方案、取舍、风险和是否需要 ADR。

仅做设计，不改代码。标记所有假设和未决业务决策；不得建议用 Redis 锁替代数据库库存一致性，也不得在数据库事务内调用外部网络。
```

## 4. 架构/方法反向评审

```text
请作为独立的严格 reviewer，审查下面的方案，不要先替作者辩护。
需求/PRD：[内容/链接]
方案/差异：[内容/链接]

按风险严重度列出具体问题，每项包括：位置/前提、触发场景、影响、为什么现有方案不足、最小修正建议。重点检查：
- 需求遗漏、错误假设、范围膨胀；
- 租户越权、IDOR、Filament UI-only 权限、队列/导出/缓存隔离；
- MySQL 约束、锁顺序、并发竞态、死锁、超卖和退款超额；
- 重复/乱序支付回调、幂等键作用域、Outbox 丢失/重复/重放；
- 迁移对滚动发布、旧 worker、回滚和历史数据的兼容；
- PII/密钥泄漏、Webhook 验签和审计缺失；
- 测试覆盖与观测/告警不足。

结尾给出 Blocker / Must fix / Should fix / Nit 列表，明确哪些问题阻止实现或发布。设计层面的快速安全扫描可用本模板；深度安全/隐私威胁审查见模板 9。不要把未验证的推测写成事实。
```

## 5. ADR 起草

```text
根据已评审的设计决策起草 ADR，状态标为 Proposed，不代表已经批准。
背景：[问题和约束]
决策问题：[需要选择什么]
备选方案：[已评估方案]
评审意见：[阻断/非阻断]

按 ADR 模板章节写（章节结构与 `docs/adr/0001-module-structure.md` 一致）：标题、状态、背景、决策驱动因素、备选方案（收益/代价）、拟议决策、后果/风险、数据迁移与回滚、验证方式、复核触发条件、决策人/日期待填。不要把业务 TBD 伪装成技术结论。
```

## 6. 拆分任务与分支计划

```text
把已批准的 PRD/设计拆分为可独立审查和发布的小任务。
PRD：[链接]
批准设计/ADR：[链接]

输出依赖 DAG 和任务清单，每项含：目标、涉及模块/文件（如可确定）、API/Schema 变化、验收标准、测试、风险、是否需要文档、估算相对规模。按垂直切片优先，避免一个巨大“实现全部功能”任务。

提出 feature/<issue>-<name> 或 fix/<issue>-<name> 分支建议、PR 顺序、是否需要 expand-and-contract 多阶段迁移，以及每个阶段的可回滚边界。不要假定能修改 GitHub 分支保护设置。
```

## 7. 编码实现（限已批准范围）

```text
现在执行以下已批准任务，不扩大范围。
任务/Issue：[内容/链接]
PRD 验收标准：[列表]
批准设计/ADR：[链接]

先给简短实现计划和预期修改文件，等我确认（若本会话已经明确授权直接实现则可继续）。实现要求：
- 遵循 AGENTS.md 与 docs/rules/；检查实际依赖及已有代码模式；
- 控制器/Filament 保持薄，业务规则放入正确模块的应用用例；
- 可信 TenantContext + Policy 授权，拒绝越权；
- 正确使用 MySQL 事务/约束，幂等，关键副作用按设计写 Outbox；
- 加 migration、Pest 测试、工厂/文档（适用时）；
- 不添加未经批准的依赖，不删除/跳过测试或放宽安全门禁；
- 不写入真实秘密或个人数据，不执行生产写操作。

完成后总结修改、设计取舍、潜在风险、执行过的精确命令及结果、未运行项。遇到与批准设计冲突、需求不确定或破坏性迁移时停止并询问。
```

## 8. Pest 测试设计/补齐

```text
根据 PRD 验收标准和当前实现，设计并实现针对本功能的 Pest 测试。
代码/PR：[链接或路径]
验收标准：[列表]

先列测试矩阵，至少考虑成功、无效输入、未认证/权限不足、跨租户访问拒绝、重复/幂等、状态边界、事务回滚、外部依赖失败/重试。按实际风险增加库存并发、乱序支付回调、退款额度、队列重复执行测试。

遵循项目已安装 Pest 版本和测试约定，不虚构 API。优先通过公开行为验证，不为测试改弱生产安全逻辑。运行实际可行的测试并报告命令、环境和结果；未运行的 MySQL/Redis 集成项明确列出。
```

## 9. 安全与隐私审查

> 适用阶段：阶段 4（设计阶段安全/隐私威胁分析，辅助）或阶段 8（PR 深度审查，主要）。设计层面快速扫描用模板 4，深度威胁审查用本模板。

```text
对该功能做面向电商 SaaS 的安全/隐私威胁审查。
变更：[PR/代码/设计]
数据分类和调用方：[填写]

检查攻击面、资产、信任边界、滥用场景与缓解措施，重点覆盖认证/对象授权/租户隔离、Mass Assignment、Webhook 验签防重放、限流、文件上传、敏感日志、密钥、SQL/输出安全、队列上下文、导出权限和数据保留。针对发现的问题给出可复现的安全测试思路及修复优先级。
只报告代码/设计证据支持的发现；区分确认漏洞与需要验证的风险。不要对生产目标发起测试，不要生成或执行攻击性利用流程。
```

## 10. PR 描述与代码 Review

```text
请基于当前分支 diff 和实际执行结果生成 PR 描述/审查意见。
关联 Issue/PRD：[链接]
实际运行命令及结果：[粘贴，不要推断]

PR 描述包括：背景、实现、范围外事项、模块/API/Schema 变化、租户/权限与安全影响、迁移发布和回滚、测试命令与结果、监控/告警、截图（仅非敏感时）。

若做 Review，优先报告可能导致生产问题的可操作发现，按严重度排序，指出文件/代码位置、触发条件和影响；不要仅复述 diff 或提出无关风格建议。没有问题时说明审查范围及未覆盖内容��不要声称绝对无风险。
```

## 11. CI/CD 与发布检查

```text
请为本次变更生成发布检查清单，不要执行任何生产部署或数据修改。
PR/Commit：[链接]
环境与发布窗口：[填写]
迁移/配置/队列变化：[填写]

检查：CI 状态和制品来源、锁文件/镜像摘要、secret 注入、MySQL migration 兼容性、旧/新应用与 Job 并存、备份恢复、灰度步骤、健康检查、关键业务指标/告警、停止扩量条件、应用回滚和数据不可逆风险、责任人与沟通计划。
将未确认项标注为阻断项。输出 Pre-deploy / Deploy / Post-deploy / Rollback 四段操作清单，并区分自动化验证与必须人工批准的动作。
```

## 12. 上线后验收与复盘

```text
基于本次发布信息整理上线验收/复盘初稿。
发布变更与时间：[填写]
PRD 验收指标：[填写]
实际观测（错误率、延迟、队列、支付、库存、Outbox 等）：[粘贴脱敏数据]
事件/反馈：[填写]

输出：验收结果（通过/不通过/未知）、用户影响、指标对比、异常时间线、根因及促成因素（证据与假设分开）、止损/恢复、待办改进项（负责人/优先级/期限/验证方法）、需更新文档/测试/告警。不要归咎于个人或 AI，不要泄露租户个人信息。
```
